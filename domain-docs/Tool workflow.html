What Is Actually Here

// three layers of paper

1. Conceptual diagnosis (workflow.html)

Node-Edge-Bucket is the diagnostic language. Nodes = entities (WorkOrder, Technician, ApprovalGate, Status, Customer). Edges = transitions and actions (Creates, Approves, Assigns, Consumes, Updates, Notifies). Buckets = constraints that gate those edges (SLA, Budget, Permissions, API limits, Location). Four of five pain points already sit on Edges — that is the signal that event-driven + async wait is the right next move, not more node schema polishing.

2. Runnable foundation (dag-node-graph-foundation.html)

This is the concrete substrate you said is already wired:

  • docker-compose.yml — Postgres 16 + Redis 7, health-checked, schema + seed applied on first boot
  • Tables: nodes, edges, events, first projection wo_current_state
  • Event-sourced character: history is append-only; projections are derived; Matlab is read-only
  • Matlab R2026a script already selects from the projection
  • VS Code tasks + VS Enterprise Container Tools attach to the same stack
  • Everything under WSL2 filesystem — no /mnt/c path tax

One command brings the whole foundation up. That is the only “live” runtime surface right now.

3. Target EDA schema (workorder-eda-schema.html)

The full target stack is designed but not required for the next step. It maps the same Node-Edge-Bucket model onto:

How the Foundation Supports the Next Four Goals

// edge · bucket · mcp · llm
01

Actual Edges

Today an edge is a row in edges (type, from_id, to_id, props, correlation_id, occurred_at) plus a matching append to events. That is already enough to emit “WorkOrderCreated”, “ApprovalRequested”, “TechnicianAssigned”, etc. The next concrete step is a thin ingest API (C# isolated worker or minimal Node) that accepts JSON, writes the event + edge, and updates the projection. Redis is already present and reserved for the first async edge queues — no new product required. Ordering-critical edges (Approval) can stay on a single-consumer queue pattern until throughput forces a consistent-hash or Kafka move.

Postgres edges live ingest API next Redis streams next

02

Actual Buckets

Buckets are constraints that gate edges. The foundation already has a JSONB props column on nodes and edges; the target schema adds a first-class constraints store (MinIO or a Postgres table). Either way the pattern is identical: before an edge is allowed, evaluate the relevant bucket values (SLA hours, budget remaining, permission set, location). The Temporal Approval workflow already expects slaHours to be read from the constraints source rather than hard-coded. You can implement the first real Bucket as a Postgres table or a JSON file today and move it to MinIO when the object-store path is needed for raw-event archival.

JSONB props ready constraints table / bucket SLA timer wired to Temporal

03

MCP surface

MCP (Model Context Protocol) is the clean way to expose the graph and its projections to an LLM or any other tool-using agent. Because the foundation already exposes a stable, queryable projection (wo_current_state) plus the raw event log, an MCP server can offer a small set of tools:

  • list_open_work_orders
  • get_work_order_state
  • get_critical_path (once the second projection exists)
  • list_pending_approvals
  • emit_edge (write path, guarded by buckets)

No graph product change is required — the MCP server is just another process on the same Docker network that speaks SQL (or later Gremlin) and returns structured results. The existing VS Code / VS tooling already lets you run and debug that process next to the compose stack.

MCP server process tool schemas over projections

04

LLM that answers

Once MCP tools exist, any LLM (local or remote) that speaks MCP can answer questions against live state instead of hallucinated schema. The same projections that Matlab already reads become the ground truth the model is allowed to see. Critical-path and betweenness numbers can be pre-computed by the scheduled MATLAB job (or a pure SQL recursive CTE) and exposed as another tool, so the model never has to invent graph theory. The event log gives the model an audit trail when it needs to explain “why is this still PendingApproval?”

MCP-capable LLM client answers grounded in projections

Critical Path From Here

// sequential

Do not expand the graph product yet. Grow capability on the existing Postgres + Redis foundation until the first real answers appear.

Foundation up → Ingest API (emit edge + event) → Constraints / first Bucket → Approval edge with wait + SLA → MCP tool server → LLM answers from tools

JanusGraph, full MinIO lake, Prometheus/Grafana, and the custom alien-purple dashboard remain valid later phases. They are not on the path to the first grounded answer.

What You Deliberately Do Not Need Yet

// postpone
  • JanusGraph / Cassandra / Elasticsearch — recursive CTEs + the existing edges table are enough for the first critical-path calculation
  • Full MinIO + lifecycle rules — a Postgres constraints table or a local JSON file is a valid first Bucket
  • Kafka / Redpanda — Redis Streams or a dedicated RabbitMQ queue (when you add it) covers the first ordered edge
  • Custom dashboard — Grafana or even a simple query against the projection is enough until the MCP/LLM path is producing answers
  • Any paid observability or workflow SaaS — Temporal (when you add it) and the existing compose stack stay self-hosted

System Character Already Set

// does not change
  • Every business action becomes a typed edge (append-only)
  • Projections are the only thing dashboards, Matlab, MCP, and the LLM are allowed to read for “current truth”
  • Buckets gate edges before they are written
  • Matlab stays analytics-only — never on the write path
  • One compose file, one network, one place for VS Code and Visual Studio to attach
  • Replay is free: re-project from the event log

That character is already present in the foundation you have running. Scaling to real Edges, Buckets, MCP, and LLM is additive work on top of it — not a redesign.
